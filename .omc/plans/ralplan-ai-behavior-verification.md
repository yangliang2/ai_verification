## RALPLAN-DR Summary

### Principles（原则）
1. **评测先行**：验证 Agent 的每一次能力改进都必须能被注入基准度量——不能度量的能力提升不算数。
2. **真实性优先于规模**：注入的缺陷必须是"AI 写 Kotlin 时真实会犯的错"，宁可补充人工审核也不灌水凑数。
3. **吞吐即架构**：单缺陷验证周期（构建→安装→执行→判定）是一等设计约束，所有组件选型先过吞吐账。
4. **报告诚实**：风险报告必须显式区分"验证过的场景 / 未覆盖的场景 / 规格盲区发现"，不制造虚假确定性。
5. **开源练兵、真实落地**：全管线先在开源 Android 宿主跑通并定标，再迁移 ColorOS 一方应用。
6. **异源对抗**（共识修订新增）：缺陷注入方与验证判定方不得共享同一模型族——打破"AI 注入的缺陷恰好是 AI 容易验出的缺陷"的认知共谋，定标抓取率必须在异源对抗下测得才可信。
   **模型族定义（Critic 修订，承重术语）**：按供应商基础模型谱系划分——Anthropic Claude 系、OpenAI GPT 系、Google Gemini 系互为不同族；同一供应商的不同版本（如 Claude 3.x 与 4.x）视为**同族**。合规判定可执行：注入侧 provider ≠ 验证侧（计划生成 + L3 oracle）provider。
   **已记录张力：P6 异源 ↔ Driver 3 单人业余维护**——异源使 API 接入/凭据/成本面翻倍，且引入双模型版本漂移这一新的不确定源，与"故障可快速定位"相抵。取舍：异源**仅强制用于定标评测跑**（AC4/AC8/AC7 里程碑口径）；日常自用验证允许同源（其结果不作为对外可信数字）；两族均走 OpenAI 兼容端点以压低接入维护成本。**Fallback**：若双族成本对业余投入不可承受，降级为"同源 + 金标准对照集 + flaky_pool 双锚"，且所有报告显式标注"同源测量，存在共谋风险折扣"。

### Decision Drivers（决策驱动，Top 3）
1. **吞吐张力**：100+ 注入缺陷 × ≥80% 抓取率 × 本地 1-2 台真机——单缺陷全周期必须压到分钟级。
2. **基准可信度**：缺陷必须行为层（生命周期/导航/系统事件/并发）、可触发、可判定、非等价变异。
3. **自用与业余投入**：单人维护，组件必须可独立演进、故障可快速定位，避免重基建。

### Viable Options（核心决策：缺陷注入方式）

**Option A：源码级 AI 变异注入（推荐）**
- 做法：AI 读宿主 Kotlin 源码，按行为层缺陷分类法生成变异 patch（如删除 `onSaveInstanceState` 恢复逻辑、协程作用域误用、生命周期回调遗漏），批量合入构建。
- Pros：最接近 AI 生成代码的真实缺陷形态；ground truth 是 diff，与验证 Agent 的输入契约（SDD+diff）同构；缺陷可解释、可分类。
- Cons：每批需重新构建安装；缺陷间可能相互干扰；存在等价变异（不改变可观察行为）需过滤。

**Option B：字节码/运行时故障注入**
- 做法：构建期 instrumentation 或运行时 hook，在执行中触发故障（如强制清状态、延迟回调）。
- Pros：单次构建可开关多种故障，吞吐高。
- Cons：注入的是"环境故障"而非"代码缺陷"，与"验证 AI 生成代码"的目标错位；基准真实性差，抓取率数字失去说服力。

**决策：Option A 为主，B 不采纳。** 真实性是这个基准存在的意义（Principle 2 压倒吞吐便利）。吞吐张力通过下述三项工程手段化解：
1. **批量注入**：每次构建合入 N 个互不干扰的缺陷（按模块/页面隔离，静态检查 patch 触碰文件不相交），摊薄构建成本。
2. **场景定向验证**：验证 Agent 拿到缺陷 diff 后只跑相关场景簇，不做全 App 漫游（与真实使用模式一致：验证一次改动）。
3. **判定前移**：crash/ANR/状态断言等廉价 oracle 先行，LLM 视觉/语义判定只在廉价信号不足时介入。

### 次级决策：App 驱动方式
- **混合驱动**：场景步骤由 LLM 基于 accessibility tree + 截图驱动（适应 UI 变化、无脚本维护）；**系统事件由 harness 确定性编排**（旋转、后台杀、权限撤销、网络切换走 adb 指令，不依赖 LLM 时机），保证缺陷触发条件可复现。
- 排除纯脚本回放（违背"零人工脚本"验收）与纯 LLM 自由探索（触发不可复现，抓取率无法归因）。

### 第三决策：基准可信度锚（共识循环第 1 轮，响应 Architect 钢人反论）
Architect 指出本架构最大风险是**同源共谋**：若注入与验证同模型族，AI 倾向注入的缺陷恰是 AI 易验出的缺陷，真正危险的缺陷系统性缺席，抓取率越高可能只说明基准越简单。三项对策：
1. **金标准对照集**：手工固化 10-15 个**非 AI 生成**的真实行为缺陷（来源：自己历史项目真实 bug、开源 issue 已关闭的真实行为缺陷），单列 holdout，不进 AI 注入主库。里程碑抓取率必须**分别报告**："AI 注入库抓取率" vs "金标准集抓取率"，两者差距即同源盲区的直接度量。
2. **强制异源**：`bench/injector/` 与 `agent/`（计划生成与 L3 oracle）使用不同模型族（如注入 Claude / 验证 GPT，或反之），写入 ADR 作为显式约束。
3. **难复现缺陷池（flaky_pool）**：AC2 过滤掉的不稳定缺陷（复现率 <2/3 但编译通过且确实改变行为）不丢弃，单独入池并记录复现率分布；不进主抓取率分母，作为高价值挑战集定期人工抽检——化解"真实性 vs 可度量性"张力，避免基准被双重提纯成"只剩好抓的"。

## Requirements Summary
- 双子系统：**验证 Agent**（输入 SDD 规格+diff+可构建源码 → 验证计划 → 真机执行 → 风险报告）与 **AI 缺陷注入评测系统**（构建 100+ 行为层缺陷基准，度量抓取率）。
- 环境：Android/Kotlin；执行底座本地 ColorOS 真机（1-2 台）+ adb；练兵宿主为开源 App。
- 缺陷类型五类：生命周期、旋转/配置变更、后台杀进程、页面导航状态、协程并发。
- 规格是不充分信号：报告须包含"规格盲区发现"。

## Acceptance Criteria（验收标准，全部可测试）
- [ ] AC1 注入管线：给定开源宿主工程，自动产出 ≥100 个行为层缺陷变体（五类各 ≥15），每个含：变异 diff、触发场景描述、预期失败表现（ground truth 三元组）。
- [ ] AC2 缺陷有效性：每个入库缺陷通过"可检测性验证"——在已知触发步骤下能稳定复现失败表现（≥2/3 次；**该门限为经验初值，Phase 2 首批 20 个缺陷实测复现率分布后复核并记录于 validator 报告**），等价变异自动剔除；**被过滤的不稳定缺陷入 flaky_pool 留痕（含复现率分布），不得静默丢弃**。
- [ ] AC3 验证闭环：给定一次代码改动（diff+规格），Agent 零人工脚本完成：验证计划生成 → 真机执行（含系统事件编排）→ 风险报告输出。口径拆分（Critic 修订）：**单缺陷验证周期（不含批构建摊销）≤12 分钟 p50；单批构建+安装 ≤20 分钟**，两个数字分别计量。
- [ ] AC4 第一里程碑：在 ≥100 缺陷 AI 注入基准上整体抓取率 ≥80%，且五类中每类 ≥60%（防止单类刷分）；**注入与验证使用不同模型族的前提下测得**。
- [ ] AC5 误报可控：对 20 个无缺陷对照改动（clean diff）误报率 ≤20%；**其中 ≥8 个必须是"看似危险实则正确"的改动**（如重构生命周期但行为等价、迁移协程作用域但语义不变），防止对照组过易导致数字虚高。验收方式：此 8 个为**人工策划并逐个标注理由的清单项**（checklist 核验，非脚本断言；此处"人工"指评测集构造阶段，非运行时驱动，不违反 AC3 零脚本）。
- [ ] AC6 规格盲区：报告含"规格未覆盖场景"章节，在基准中由"规格故意留白"的缺陷子集（≥10 个）验证其发现能力。
- [ ] AC7 迁移验证：注入管线与验证 Agent 在 1 个 ColorOS 一方应用模块上跑通端到端小样本（≥10 缺陷），**同样在异源约束下执行**（定标口径一致）。
- [ ] AC8 金标准对照（Blocking，Architect 必须项 1）：建成 ≥10-15 个非 AI 生成的真实缺陷金标准集；M3 报告必须**分别报告** AI 注入库抓取率与金标准集抓取率，并对两者差距做盲区分析。分级动作（Critic 修订）：≥60% 达标；**40-60% = 监控带——记录差距分析、不阻塞门禁，连续两轮迭代无改善则升级为告警**；<40% = 基准可信度告警，须回到注入分布校准。
- [ ] AC9 全基准周期 SLO（Blocking，Architect 必须项 3）：Phase 0 选定宿主后实测单批可并行不相交缺陷数 K（要求 K ≥8），全基准构建轮数 = ⌈100/K⌉。**预算账（Critic 修订，可校验）**：K=8 时约 13 批 × ≤20min 构建 ≈ 4.3h，+ 100 × ≤12min 验证 ÷ 2 台 ≈ 10h，合计 ≈14.3h（p50 口径估算，系统性低估长尾——**约 10h 余量的设计意图正是吸收 LLM 驱动重试、flaky 复跑与 p90+ 长尾**）——**全基准一轮墙钟 ≤24 小时**（该余量须同时覆盖 AC2 validator 复现跑的设备占用，Phase 0 实测时一并计入）。重定标边界：Phase 0 实测后允许**一次性**重定标且硬上限 ≤48 小时；预测超 48h 必须更换宿主或调整 K，不得继续放宽。**兜底**：若所有候选开源宿主实测 K 均 <8，降级路径为"双宿主分摊基准"或"接受更多构建轮数但锁 48h 硬上限"，并记录于定标报告。
- [ ] AC10 基准版本化（Critic 建议采纳）：基准结果绑定版本号（基准库版本 + 验证侧模型版本）；若发现验证侧模型存在系统性盲区或基准库变更，受影响版本的抓取率数字作废并复跑，禁止跨版本混报。

## Implementation Steps（实施步骤）

### Phase 0：设备与构建底座（基础设施）
1. `harness/device/`：adb 设备编排层——应用安装/启动/清数据、**系统事件原语**（`adb shell` 旋转、`am kill` 后台杀、`pm revoke` 权限、`svc` 网络开关、低存储/电量模拟）、屏幕/accessibility tree 采集、logcat/crash/ANR 捕获。
2. `harness/build/`：宿主工程批量构建管线——patch 应用、增量构建、产物缓存、按缺陷批次出 APK。
3. 选定 1-2 个开源宿主 App（标准：Kotlin、活跃维护、含典型架构 ViewModel/Compose 或 View、可本地构建、有一定页面复杂度，**且可隔离注入点充足——实测单批不相交缺陷数 K ≥8**，宿主选型是吞吐链的架构决策而非普通选型），fork 固定版本。
3b. **ColorOS 构建探路（从 Phase 4 前置，Architect 建议 8）**：并行启动内部构建系统对接可行性探查（签名、构建入口、产物安装权限），目标是尽早证伪——若构建壁垒不可逾越，Phase 4 退化方案（仅迁移验证 Agent、注入留开源宿主）需提前确认。
3c. **金标准对照集启动（Architect 必须项 1）**：开始从自己历史项目真实 bug 与开源 issue 中收集非 AI 生成的行为缺陷素材（目标 ≥10-15 个），与基建并行推进。

### Phase 1：验证 Agent 最小闭环（先于注入系统，用手工种子缺陷）
4. `agent/planner/`：验证计划生成器——输入 diff+规格 → 输出场景簇（目标页面、操作序列意图、需编排的系统事件、预期行为、规格盲区猜想），结构化 JSON。
5. `agent/driver/`：LLM 驱动执行器——按场景簇驱动真机（accessibility tree 优先、截图兜底），harness 在指定步骤注入系统事件；全程录制执行轨迹。
6. `agent/oracle/`：分层判定——L1 crash/ANR/异常日志，L2 状态断言（旋转/杀进程后 UI 状态恢复比对），L3 LLM 语义判定（行为是否符合规格/常理）；输出带证据链的判定。**判定输出 schema 在本阶段冻结**（字段含：缺陷类别假设、触发步骤、证据类型 L1/L2/L3、证据原文/截图引用、置信度），保证 Phase 3 按模式归因有结构化数据（Architect 建议 9）。
7. `agent/report/`：风险报告生成——验证了什么/结论与证据/未覆盖场景/规格盲区发现。
8. **里程碑 M1**：从金标准对照集取 5 个种子缺陷植入宿主，Agent 端到端抓住 ≥3，闭环成立——同时验证对照集机制本身（Architect 建议 7：不再使用临时手工种子）。

### Phase 2：AI 缺陷注入管线
9. `bench/taxonomy/`：行为层缺陷分类法——五大类 × 典型模式（每类 5-8 个模式，来源：Android 官方陷阱文档、自身踩坑记录、开源 issue 挖掘）。
10. `bench/injector/`：AI 变异生成器——按分类法对宿主源码定点生成变异 patch + 触发场景 + 预期表现（ground truth 三元组）；静态过滤（编译通过、触碰文件不相交才同批）。**注入模型与验证侧模型强制异源（Architect 必须项 2）**。
11. `bench/validator/`：可检测性验证器——对每个缺陷按 ground truth 触发步骤复现，剔除等价变异（AC2）；**不稳定缺陷分流入 `bench/flaky_pool/` 留痕，记录复现率分布，作为高价值挑战集**。
11b. `bench/goldset/`：金标准对照集固化——将 Phase 0 收集的真实缺陷素材移植到宿主 App，人工验证可触发性，单列 holdout 库（AC8）。
12. **里程碑 M2**：AI 注入基准库 ≥100 有效缺陷（五类各 ≥15，含 ≥10 个"规格留白"缺陷）+ 金标准对照集 ≥10 个就绪 + flaky_pool 机制运转。

### Phase 3：规模化评测与能力迭代
13. `bench/runner/`：评测调度器——缺陷批次 × 设备队列，断点续跑，结果入库（SQLite 即可）。
14. 跑全量基准 → 抓取率分析（按类/按模式归因）→ 迭代 Agent（计划生成 prompt、oracle 断言、驱动稳定性）→ 复测。每轮迭代输出对比报告。
15. clean diff 对照组测误报（AC5）。
16. **里程碑 M3 = 第一里程碑**：AI 注入库整体抓取率 ≥80% 且各类 ≥60%；**金标准集抓取率分别报告（目标 ≥60%，<40% 触发基准可信度告警）**；误报 ≤20%（含高难度 clean diff）；全基准一轮墙钟 ≤24h（AC9）。

### Phase 4：ColorOS 迁移验证
17. 选 1 个一方应用模块，适配构建管线（内部构建系统对接为主要风险，提前一周探路）；小样本 ≥10 缺陷端到端（AC7）。
18. 产出迁移差异报告：开源宿主与一方应用在驱动成功率、判定准确率上的差距与原因。

## Risks and Mitigations
| 风险 | 影响 | 缓解 |
|------|------|------|
| 吞吐不达标（单缺陷 >15min） | 100+ 基准跑不完 | 批量注入摊薄构建；场景定向验证；判定前移；两台设备并行 |
| 等价变异污染基准 | 抓取率数字失真 | AC2 可检测性验证强制门禁，进库前复现 ≥2/3 |
| LLM 驱动不稳定（UI 操作失败） | 假阴性，抓取率被驱动问题拖累 | 驱动失败与"未抓住缺陷"分开归因统计；accessibility tree 优先于视觉 |
| LLM oracle 误判 | 误报/漏报 | 分层判定，L1/L2 廉价信号优先；L3 判定必须附证据链；AC5 对照组 |
| **同源 AI 认知盲区共谋**（Architect 钢人反论） | 抓取率自我膨胀，高分无意义，真实使用时崩塌 | 注入/验证强制异源模型族；非 AI 金标准对照集分别报告；flaky_pool 防基准被提纯成"只剩好抓的" |
| 注入缺陷分布偏离真实 AI 错误分布 | 基准说服力打折 | 分类法来源含真实踩坑与开源 issue；定期用自己项目的真实 AI 缺陷回填校准；金标准集差距分析定向修正注入分布 |
| ColorOS 构建/签名/权限壁垒 | Phase 4 卡死 | 推迟到管线已在开源宿主验证后；提前探路构建系统；最坏退化为"仅验证 Agent 迁移、注入留在开源宿主" |
| 业余投入断档 | 项目烂尾 | Phase 顺序保证每阶段独立可用（M1 后 Agent 已可自用于日常改动验证） |

## Verification Steps
1. 每个 AC 对应一条可执行检查：AC1/AC2 由 `bench/validator` 出库统计；AC3 由 runner 计时日志；AC4/AC5 由评测报告；AC6 由留白子集命中率；AC7 由迁移运行记录。
2. M1/M2/M3 里程碑各出一份证据报告（执行日志+轨迹录屏+判定证据链），不凭口头宣布达成。
3. 第一个真实自用验证：M1 后即在自己日常 AI 改动上试用，记录真实抓获/漏过案例回填基准。

## ADR
- **Decision**：源码级 AI 变异注入（Option A）+ 混合驱动（LLM 操作 + harness 确定性系统事件编排）+ 分层 oracle；**注入与验证强制异源模型族；非 AI 金标准对照集作为抓取率可信度锚**；先开源宿主后 ColorOS（构建探路前置 Phase 0）。
- **Drivers**：基准真实性（注入的须是 AI 真实会犯的代码错误）；本地真机吞吐约束（全基准墙钟 ≤24h）；单人业余可维护；**评测闭环不得同源自证**。
- **Alternatives considered**：字节码/运行时故障注入（真实性差，拒绝）；纯脚本回放驱动（违背零脚本验收，拒绝）；纯 LLM 自由探索（不可复现，拒绝）；云真机平台起步（重基建，推迟）；**注入/验证共用同一模型（默认方案，被 Architect 钢人反论否决——认知共谋使抓取率失去意义）**。
- **Why chosen**：A 与验证 Agent 输入契约同构，ground truth 即 diff，抓取率可直接归因到"验证 AI 代码改动"这一目标能力；异源+金标准双锚使该归因可信。
- **Consequences**：必须投资批量构建管线与等价变异过滤；需维护两个模型族的接入；吞吐与金标准差距是持续监控项；基准不可完全公开（含一方应用部分）。**免责声明：provider 异源是共谋去相关的可操作代理，不等价于训练谱系完全独立——不同 provider 间训练语料重叠造成的弱共谋无法由该判据识别。**
- **Follow-ups**：真实缺陷回填校准机制；两台以上设备并行调度；flaky_pool 定期人工抽检节奏；接入形态封装（规格中已推迟）；**一方应用源码喂外部异源 provider 做 L3 判定的数据合规边界，须在 Phase 4 启动前与内部合规确认**（Critic 终审提示——若不可出境，L3 oracle 在 ColorOS 阶段降级为内部部署模型或 L1/L2-only）。
