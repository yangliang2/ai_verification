# Android CLI first execution base

MVP execution uses Google's Android CLI (`android`) as the first-class interface for open-source Android host automation because it is built for agent-first workflows and exposes project/device/layout/screenshot/docs/skills capabilities from the terminal. Android CLI-supported Journeys are the primary MVP UI execution path through the chosen agent and Android CLI skills; this project runner must not assume a standalone `android journey run` subcommand unless the installed CLI exposes one. The runner is responsible for orchestration, system-event injection, evidence collection, oracle evaluation, reporting, and benchmark accounting rather than reimplementing a full LLM UI driver. We still keep adb as a fallback for low-level system-event primitives and logcat control that Android CLI does not cover precisely enough, such as rotation, background process kill, permission revocation, network toggles, and filtered crash capture.

Evidence capture follows the same rule, with one device-identity exception. Android CLI remains the first choice for layout capture and for screenshots when a run does not name a device, but Android CLI 1.0.15498356 does not expose a device selector for its screenshot command. Whenever a run names an explicit serial, the collector therefore captures the raw screenshot with three recorded, serial-scoped adb commands: `adb -s <serial> shell screencap -p <remote-path>`, `adb -s <serial> pull <remote-path> <local-path>`, and `adb -s <serial> shell rm -f <remote-path>`. This controlled fallback is used regardless of the number of connected devices, prevents implicit-device attribution, and leaves Android CLI annotated screenshots unavailable for that capture. When no serial is named, the collector continues to use `android screen capture`.

The verification plan schema stays driver-agnostic. A Journey adapter converts `ScenarioCluster` objects into Android CLI Journey instructions while the runner keeps system-event timing outside the Journey so the same plan can later target a deterministic driver or another execution backend.

Smoke and M1 use agent-in-the-loop execution: the runner produces structured Journey instructions, checkpoints, and evidence contracts, while the current coding agent performs UI navigation with Android CLI layout/screenshot tools and adb input. Fully unattended Journey execution is a later capability upgrade and is not a smoke/M1 acceptance gate.
